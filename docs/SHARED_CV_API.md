# Контракт внешнего CV API

## Статус

Это **предлагаемый контракт клиента**, а не подтверждение существования сервиса
в shared-infrastructure. Реализация провайдера и endpoint должны быть согласованы
владельцем общей инфраструктуры. До этого `VISION_ENABLED=false`.
`shared-vlm` с OpenAI Chat Completions не предоставляет этот контракт автоматически.
Захват и живой просмотр работают независимо от данного API.

## Запрос

`VISION_INFERENCE_URL` — полный HTTP(S) endpoint, например путь `/v1/person-tracks`
согласованного CV-сервиса. Адрес модели, GPU или веса в приложение не передаются.
При наличии `VISION_INFERENCE_TOKEN` добавляется `Authorization: Bearer <token>`.
Токен не передаётся в URL. Это авторизация будущего CV API, а не обязательный
ключ для существующего shared-vlm.

POST `multipart/form-data`:

| Поле | Значение |
| --- | --- |
| `version` | строка `1` |
| `camera_id` | UUID камеры |
| `session_id` | непрозрачный уникальный идентификатор tracking-сессии |
| `sequence` | возрастающий номер запроса внутри сессии, начиная с `1` |
| `captured_at` | ISO 8601 времени исходного кадра с timezone |
| `image` | исходный JPEG, `Content-Type: image/jpeg`, filename `frame.jpg` |

Реквизиты RTSP, адрес камеры, пароль и данные пользователей не отправляются.
Session меняется при reconnect, смене конфигурации и длительном пропуске кадров.
Вызовы одной камеры последовательны; пропуски sequence допустимы. Tracker должен
быть изолирован по `camera_id + session_id`, принимать возрастающие кадры и
очищать завершённые/неактивные сессии по ограниченному TTL.

## Ответ

HTTP 200, JSON:

```json
{
  "version": 1,
  "camera_id": "UUID отправленной камеры",
  "session_id": "идентификатор отправленной сессии",
  "sequence": 1,
  "tracks": [
    {"track_id": 24, "confidence": 0.91, "bbox": [0.1, 0.1, 0.4, 0.9]}
  ]
}
```

Первые четыре поля должны точно совпадать с запросом. `tracks` содержит только
людей: bbox `[x1,y1,x2,y2]` в диапазоне `[0,1]`, `x1<x2`, `y1<y2`, confidence
от 0 до 1; `track_id` — неотрицательное целое, уникальное в одном ответе и
устойчивое для одного человека в одной сессии. Максимум 256 tracks. Пустой список
означает отсутствие людей. Клиент отвергает некорректные, чужие и несовместимые
результаты; такие ответы не создают нарушения.

Модель person detection и ByteTrack либо эквивалентный tracker размещаются
централизованно. CV runtime отвечает за загрузку весов, GPU-размещение, лимиты,
backpressure и жизненный цикл треков. Автоматических повторов POST в клиенте нет.
По умолчанию сетевые timeout — 2 секунды; при отказе следующий свежий кадр
обрабатывается независимо. Очередь кадров не накапливается.

## Приёмка перед включением

1. Подтвердить поддержку описанного API, изоляцию сессий и нормализованные bbox.
2. Проверить stable IDs на пересечении линии, reconnect и пропусках кадров.
3. Измерить фактическую задержку, частоту обработанных кадров и нагрузку shared
   GPU на реальном количестве камер. Сейчас worker обрабатывает запросы
   последовательно; настройки fps не гарантируют производительность inference.
4. Проверить нагрузку CPU-декодирования и памяти при выбранном RTSP разрешении.
5. Подтвердить отсутствие деградации других shared моделей и ограничение очередей.
6. Указать реальный endpoint, при необходимости токен и `VISION_ENABLED=true`,
   затем выполнить контейнерные проверки и `watch.sh deploy`.
7. На реальном видео проверить направление, расписание, JPEG/PDF доказательства
   и отдельно разрешённые внешние уведомления.

Правила пересечения и доказательств покрыты синтетическими tests. Производительность
и качество распознавания требуют проверки фактического shared CV runtime.
