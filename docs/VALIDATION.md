# Проверка изменений

## Выполненные проверки

Windows: 131 Python tests прошло, включая 5 Chromium E2E; 4 integration tests
реальных PostgreSQL/Redis/RabbitMQ пропущены, поскольку локальный Docker daemon
недоступен. Ruff check/format, Django check и отсутствие новых миграций,
Compose config для ops/tests/inference, Bash syntax и 3 Node tests прошли.
Branch coverage всего проекта — 80%; публикация CPU-кадра, обмен исходными JPEG
и валидация CV-ответа покрыты полностью в локальном прогоне.

Проверены: показ защищённого JPEG без inference, публикация live до отказа
передачи исходника, отключение камеры, запрет двойного decoder, изоляция отказов,
свежесть/дубликаты/reconnect кадров, бинарный Redis-пакет с TTL, внешний API
с camera/session/sequence и нормализованными person tracks, скрытие токенов,
сохранение правил пересечения/расписания/evidence и отсутствие GPU/ML runtime.
Свежий Celery process загружает Django и регистрирует задачи без внешнего broker.
Контейнерный test проверит реального Celery consumer с проектными правами.

В предоставленном предыдущем серверном прогоне: 105 прошло, 1 падение из-за DNS
RabbitMQ. Среди запущенных контейнеров shared-rabbitmq-1 отсутствовал.
Новая предпроверка обнаруживает недоступный DNS/AMQP до сборки тестового образа;
provisioning сообщает состояние/неудачную команду без пароля.
В последнем выводе камеры подтверждён доступ к 192.168.55.9:554, но отсутствовали
capture/vision и ключи `warehouse:frame:*`. Постоянный CPU capture устраняет эту
зависимость просмотра от VISION_ENABLED. Реальный RTSP проверяется на сервере.

## Сервер после публикации владельцем

```bash
cd /home/main/projects/watch-service
git pull --ff-only origin main
sed -i '/^VISION_\(ENABLED\|DEVICE\|GPU_ID\|MODEL\)=/d' .env
# Если существующий shared брокер остановлен, оператор запускает его:
docker start shared-rabbitmq-1
bash scripts/watch.sh rabbit shared-rabbitmq-1
bash scripts/watch.sh test-containers
bash scripts/watch.sh deploy
bash scripts/watch.sh status
```

`deploy` повторяет tests до миграций. При падении проверки рабочие процессы не
пересоздаются. В status должны быть web, camera-capture, PostgreSQL, Redis,
notification-worker и scheduler. Inference отсутствует до согласования CV API.

## Ручная приёмка

1. Через HTTPS proxy или SSH-туннель на localhost:8086 войти в `/login/`, открыть
   кабинет с меню, карточками, статистикой и историей по `renders/img.png`.
2. Открыть «Камера_1» с проверенным RTSP. Подождать 5–10 секунд, нажать «Обновить
   кадр»: появится фотография камеры; в мониторинге — обновляющееся изображение
   и LIVE. Это работает при VISION_ENABLED=false, без модели и GPU.
3. Сохранить контрольную линию и обновить страницу: координаты остаются, линия
   видна. Изменить параметры камеры: capture подхватывает их без рестарта web.
4. Отключить камеру: кадр становится недоступен, ложного LIVE нет. Снова включить
   и дождаться изображения. Кадры и stream недоступны без входа.
5. Проверить порядок/сетку мониторинга, fullscreen и сохранение раскладки.
6. Проверить недельное расписание, настройки хранения, CSV/PDF и старую историю.
7. Проверить управление получателями. При выключенных серверных флагах внешняя
   тестовая отправка недоступна. Notification-worker не должен перезапускаться.
8. После подключения согласованного shared CV API проверить производительность,
   устойчивость track IDs, пересечения и расписание на реальном видео, JPEG/PDF
   доказательства и отдельно разрешённые Email/Telegram.

Синтетические tests не подтверждают качество CV runtime, пропускную способность
на всех RTSP-камерах и совместимость API фактического shared сервиса.
